# BUG-001: Stripe subscription flows return to a nonexistent route

> RETRACTED in Phase 4. `src/middleware.ts:11-16` and `34-42` implement `/dashboard` as a redirect to `/text-to-video`, disproving the original 404 premise. The regression and fix patches below are deprecated and must not be applied.
> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-08-04 · Project: VideoFly

## 1. Summary

Subscription checkout and Billing Portal use `/dashboard` at `src/services/billing.ts:140-146` and `269-304`, but the application has no dashboard page. External payment activity can finish successfully and then return the customer to a 404.

## 2. Spec reference

REQ-009 requires every Stripe return destination to resolve to a real account page. The behavioral contract is: “every Stripe return URL resolves to an existing application route.”

## 3. The code

Both portal and subscription checkout construct `${NEXT_PUBLIC_APP_URL}/dashboard`; the actual account page is `src/app/[locale]/(dashboard)/settings/page.tsx`.

## 4. Observable consequence

A successful payment, cancellation, downgrade portal, or existing-customer portal session redirects to a missing page. The economic event may still be correct, making the navigation failure especially confusing.

## 6. The fix

Use the existing `/settings` route and preserve a success marker for checkout.

```diff
-      ? `${process.env.NEXT_PUBLIC_APP_URL}/dashboard`
-      : "/dashboard";
+      ? `${process.env.NEXT_PUBLIC_APP_URL}/settings`
+      : "/settings";
@@
-      success_url: returnUrl,
+      success_url: `${returnUrl}?checkout=success`,
```

## 7. The test

Apply `BUG-001-regression-test.patch` and run its Vitest file. Unpatched code fails because `/dashboard` is present and no matching page exists; patched code passes with `/settings`.
