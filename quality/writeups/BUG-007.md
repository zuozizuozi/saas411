# BUG-007: DNS safety check is not bound to the media connection
> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-08-05 · Project: VideoFly

## Summary

`fetchSafeRemoteMedia()` validates one DNS resolution but later connects by hostname through `fetch()`, allowing the address used by the connection to differ from the validated address.

## Spec reference

- Requirement: REQ-010
- Spec basis: `quality/REQUIREMENTS.md:151-162`
- Behavioral contract quote: "actual HTTP connection uses an address that passed public-network validation"

## The code

At `src/lib/storage.ts:72-79`, `assertSafeRemoteMediaUrlResolved()` resolves and validates all addresses. At `src/lib/storage.ts:104-109`, `fetch(currentUrl)` performs a separate hostname resolution with no pinned dispatcher or custom lookup.

## Observable consequence

With a provider-controlled hostname that first resolves publicly and then rebinds to a private or link-local address, the server can connect to the private target and upload the response to R2. Every redirect repeats the same check/use separation.

## Depth judgment

The URL, redirect, byte, and timeout checks look comprehensive, so this gap is visible only by following DNS state across the validation-to-connection boundary.

## The fix

The connection must consume the validated address. This design-gated diff shows the required boundary; the helper must be implemented with proxy compatibility, redirect revalidation, bounded streaming, and dispatcher cleanup before a fix patch is approved.

```diff
 import { fetchWithValidatedAddress } from "@/lib/network/safe-fetch";
@@
-    const response = await fetch(currentUrl, { redirect: "manual", signal });
+    const response = await fetchWithValidatedAddress(currentUrl, {
+      redirect: "manual",
+      signal,
+      rejectAddress: isPrivateAddress,
+    });
```
