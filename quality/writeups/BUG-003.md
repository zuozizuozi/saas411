# BUG-003: Bailian is rejected by callback ingress
> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-08-04 · Project: VideoFly

## 1. Summary

Bailian is a valid `ProviderType`, configurable API provider, and factory implementation, but the callback route's manual list omits it at `src/app/api/v1/video/callback/[provider]/route.ts:16`.

## 2. Spec reference

REQ-011 requires provider representations to be complete or capability-aware. Contract: “callback ingress includes every callback-capable provider.”

## 3. The code

The type/config/factory contain five providers; callback ingress contains four. The executable route probe returns 400 for a valid signed Bailian callback before calling the handler.

## 4. Observable consequence

If Bailian callbacks are enabled, completions are rejected. Current polling behavior can mask the gap.

## 5. Depth judgment

If Bailian is intentionally polling-only, the deeper defect is absent explicit capability metadata. Phase 4 must decide whether acceptance or a declared exclusion is authoritative.

## 6. The fix

Use the canonical provider list for ingress; a capability registry would be stronger if polling-only is intentional.

```diff
+import { AI_PROVIDERS } from "@/ai/provider-config";
@@
-    if (!["evolink", "kie", "apimart", "zhipu"].includes(providerType)) {
+    if (!(AI_PROVIDERS as readonly string[]).includes(providerType)) {
```

## 7. The test

The regression patch mocks signature and video handling, posts a Bailian callback, and expects HTTP 200 plus one handler call. Current code is an expected failure.
