# VideoFly Behavioral Requirements
> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-08-04 · Project: VideoFly

Version: 1.0 baseline. Scope follows Phase 1 exploration and excludes marketing experience optimization and legacy Kubernetes/tRPC depth.

Total requirements: 14 (12 baseline plus REQ-013 and REQ-014 from reconciliation).

## Authentication and Authorization

These requirements define who may cross user, object, and administrator boundaries.

### REQ-001: Sensitive APIs require a valid session

- Source tier: inferred from executable authorization boundaries
- User story: As an account holder, I need anonymous callers blocked so vendor cost and private data are attributable to a real user.
- References: `src/lib/api/auth.ts:10`, `src/lib/api/auth.ts:25`, `src/app/api/v1/video/generate/route.ts:26`
- Use cases: UC-001, UC-002, UC-003, UC-006, UC-007
- Conditions of satisfaction:
  1. Credit, video, asset, upload, generation, and account endpoints return 401 without a session.
  2. Page redirects do not substitute for API authentication.
  3. The authenticated principal comes from session headers, not request-body or query user IDs.

### REQ-002: User-owned resources are isolated

- Source tier: inferred from ownership services
- User story: As a user, I need videos and source media isolated from other accounts.
- References: `src/app/api/v1/video/generate/route.ts:29`, `src/app/api/v1/video/generate/route.ts:32`, video service user-scoped queries
- Use cases: UC-002, UC-003, UC-006
- Conditions of satisfaction:
  1. Get, list, delete, retry, recover, and status operations include the authenticated user in the lookup.
  2. Every generation image URL is deduplicated and verified as owned before provider submission.
  3. A cross-user identifier returns a denial/not-found result and produces no mutation.

### REQ-003: Administrator authority is current and database-backed

- Source tier: inferred from role revocation design
- User story: As an operator, I need admin grants and revocations enforced immediately.
- References: `src/lib/api/auth.ts:36`, `src/lib/auth/admin-role.ts:7`, `src/lib/auth/admin-role.ts:12`
- Use cases: UC-007
- Conditions of satisfaction:
  1. Unauthenticated admin requests return 401 and authenticated non-admin requests return 403.
  2. The role decision reads `users.isAdmin` from the database for each authorization check.
  3. Cached session claims cannot retain revoked administrator access.

## Generation Contract

The generation surface must present and enforce one model/cost contract.

### REQ-004: Frontend and server enforce the same active model capabilities

- Source tier: inferred from shared catalog and server validator
- User story: As a user, I need displayed options and charged cost to match what the server accepts.
- References: `src/components/tool/generator-panel.tsx:253`, `src/components/tool/generator-panel.tsx:286`, `src/components/tool/generator-panel.tsx:310`, `src/app/api/v1/video/generate/route.ts:10`, `src/services/video-validation.ts:27`
- Use cases: UC-002, UC-003
- Conditions of satisfaction:
  1. Only active catalog models can be submitted.
  2. Duration, aspect ratio, quality, audio, watermark, mode, image count, and output count are server-validated.
  3. Server credit calculation uses the same model identifier, duration, quality, and output multiplier as the UI estimate.
  4. Direct API callers cannot obtain unsupported vendor options or a lower charge by bypassing UI controls.

### REQ-005: Credit and generation state changes compensate on every path

- Pattern: compensation
- Source tier: inferred from FIFO hold/settlement lifecycle
- User story: As a paying user, I need a charge exactly once for a usable completion and no frozen value after failure.
- References: `src/services/video.ts:324`, `src/services/video.ts:341`, `src/services/video.ts:546`, `src/services/video.ts:555`, `src/services/video.ts:577`, `src/services/credit.ts:359`, `src/services/credit.ts:448`
- Use cases: UC-002, UC-003, UC-004, UC-005
- Conditions of satisfaction:
  1. A user-scoped lock protects FIFO package allocation and ledger mutations.
  2. Provider submission failure releases the hold and marks the video FAILED.
  3. Storage succeeds before settlement; settlement succeeds before COMPLETED.
  4. Duplicate callback, polling, settle, or release attempts do not duplicate charges or refunds.
  5. Every terminal video has a resolved hold consistent with its outcome.

## Provider and Callback Lifecycle

Provider identities, callbacks, polling, and durable recovery must form one state machine.

### REQ-006: Callbacks are authenticated and bound to the stored task

- Source tier: inferred from signed callback design
- User story: As a user, I need vendor callbacks unable to complete the wrong video or charge the wrong task.
- References: `src/ai/utils/callback-signature.ts:39`, `src/app/api/v1/video/callback/[provider]/route.ts:26`, `src/services/video.ts:379`, `src/services/video.ts:385`
- Use cases: UC-004
- Conditions of satisfaction:
  1. Missing, expired, future-skewed, malformed, or incorrect HMAC values are rejected before parsing business state.
  2. Provider identity equals the stored provider.
  3. Parsed external task ID equals the stored task ID.
  4. Replays are idempotent and cannot settle twice.
  5. Callback JSON is rejected before unbounded memory consumption.

### REQ-007: Missed callbacks converge durably

- Pattern: parity
- Source tier: inferred from the QStash fallback purpose
- User story: As a user, I need a slow or lost callback to reach the same terminal result as the primary callback path.
- References: `src/services/video.ts:324`, `src/app/api/internal/workflows/video-reconcile/route.ts:28`, `src/app/api/internal/workflows/video-reconcile/route.ts:43`, `src/app/api/internal/workflows/video-reconcile-failed/route.ts:20`
- Use cases: UC-005
- Conditions of satisfaction:
  1. Accepted tasks schedule a signed durable reconciliation when production queue configuration is present.
  2. A processing task beyond the first polling window is requeued, explicitly timed out, or escalated to a persistent recovery queue.
  3. A terminal provider failure marks FAILED and releases credits exactly once.
  4. A terminal provider success follows the same storage/settlement path as a callback.
  5. Workflow delivery exhaustion produces an actionable persisted state, not logging only.

### REQ-011: Provider representations are complete and capability-aware

- Pattern: whitelist
- Source tier: inferred from cross-implementation parity
- User story: As an operator, I need adding a provider to either create a complete integration or fail a mechanical check.
- References: `src/ai/types.ts:3`, `src/ai/provider-config.ts:3`, `src/ai/index.ts:18`, `src/app/api/v1/video/callback/[provider]/route.ts:16`
- Use cases: UC-002, UC-003, UC-004, UC-005
- Conditions of satisfaction:
  1. Provider type, configuration, API-key mapping, factory, model mapping, routing, health, and tests use one canonical registry or mechanically verified parity.
  2. Callback ingress includes every callback-capable provider.
  3. Polling-only providers declare that capability explicitly rather than disappearing from a duplicated allowlist.
  4. Unknown providers fail closed with a stable client error.

## Payments and External Navigation

Economic events must be authentic, idempotent, and return users to a valid local state surface.

### REQ-008: Stripe economic events are authentic and idempotent

- Source tier: inferred from Stripe webhook and credit order design
- User story: As a customer, I need one payment to create one economic entitlement even when Stripe retries.
- References: `src/app/api/webhooks/stripe/route.ts:10`, `src/app/api/webhooks/stripe/route.ts:19`, credit recharge order conflict handling
- Use cases: UC-006
- Conditions of satisfaction:
  1. Missing/invalid Stripe signatures are rejected before event handling.
  2. Webhook bodies larger than 1 MiB are rejected.
  3. Event IDs and economic order numbers are claimed idempotently.
  4. Duplicate and concurrent delivery produces one plan transition or balance delta.
  5. Failed processing remains retryable without partially duplicating value.

### REQ-009: Stripe return destinations exist

- Source tier: inferred from external navigation contract
- User story: As a customer, I need checkout and portal completion to return to a usable account page.
- References: `src/services/billing.ts:140`, `src/services/billing.ts:269`, `src/services/billing.ts:277`, `src/services/billing.ts:303`
- Use cases: UC-006
- Conditions of satisfaction:
  1. Checkout success URL resolves to a route in the production build.
  2. Checkout cancellation URL resolves to a route in the production build.
  3. Billing Portal return URL resolves to a route in the production build.
  4. The destination follows the application's locale routing policy and exposes refreshed account/payment state.

## Media and Deployment Security

Both user uploads and provider-controlled downloads are hostile until verified.

### REQ-010: Media ingestion is owned, content-validated, network-safe, and bounded

- Source tier: inferred from upload/storage defenses
- User story: As an operator, I need media ingestion unable to cross user boundaries, reach private services, or exhaust memory.
- References: `src/lib/storage.ts:54`, `src/lib/storage.ts:72`, `src/lib/storage.ts:104`, `src/lib/storage.ts:119`, `src/lib/storage.ts:250`
- Use cases: UC-003, UC-004, UC-005
- Conditions of satisfaction:
  1. User uploads require a valid reservation and matching owner/key/metadata.
  2. Declared and actual image size/type plus magic bytes are validated.
  3. Provider URLs require HTTPS and reject loopback/private/link-local destinations on every redirect.
  4. The actual HTTP connection uses an address that passed public-network validation.
  5. Redirect count, time, declared length, and streamed bytes are bounded.

### REQ-012: Secrets and deployment configuration fail safely

- Source tier: inferred from environment validation and repository scan
- User story: As an operator, I need configuration errors visible before production traffic and credentials kept server-side.
- References: `.env.example:131`, `src/ai/utils/callback-signature.ts:6`, `next.config.mjs:28`, `README.md:145`, `docs/API-INTEGRATION-GUIDE.md:55`
- Use cases: UC-004, UC-005, UC-006
- Conditions of satisfaction:
  1. Production build/start validates required auth, URL, provider, callback, payment, queue, and storage variables appropriate to enabled features.
  2. Callback HMAC secret is at least 32 bytes and never exposed through `NEXT_PUBLIC_*`.
  3. Tracked files contain examples/placeholders only, not live credentials.
  4. All active deployment documentation names `CALLBACK_HMAC_SECRET` consistently.

## Account Data Contract

### REQ-013: Exposed account controls and API representations are behaviorally connected

- Source tier: inferred from rendered account controls and their typed API clients
- User story: As an account holder, I need filters and transaction labels to reflect the data contract actually returned by the server.
- References: `src/components/creation/my-creations-page.tsx:29`, `src/hooks/use-videos.ts:30`, `src/app/api/v1/credit/history/route.ts:21`, `src/components/credits/credit-history.tsx:19`
- Use cases: UC-002, UC-006
- Conditions of satisfaction:
  1. Changing a rendered status, model, or sort control changes the list query or deterministically filters/sorts the complete loaded result.
  2. The API, TypeScript types, UI configuration, and every locale use one credit transaction vocabulary or an explicit total mapping.
  3. Every transaction value returned by the API has a stable icon/label path and cannot request a missing translation key.

- Source tier: inferred from emitted analytics components and the production CSP

## Use Cases

### UC-001: Guest generator login gate
- Actor: unauthenticated visitor
- Preconditions: no valid session
- Flow: open generator, enter a valid prompt, submit
- Postconditions: login page shown; no video, hold, upload, or provider task created
- Formal document references: `docs/project-blueprint.md`, application auth routes

### UC-002: Authenticated text-to-video generation
- Actor: authenticated user with credits
- Preconditions: supported active model and sufficient available balance
- Flow: choose model/options, submit, freeze credits, bind provider task, reach terminal state
- Postconditions: usable stored video plus settled charge, or FAILED plus released credits
- Formal document references: `docs/VIDEO-OPERATIONS.md`, `docs/spec/CREDIT_CALCULATOR.md`

### UC-003: Authenticated image-to-video generation
- Actor: authenticated user with owned uploaded image
- Preconditions: completed upload reservation and sufficient credits
- Flow: select owned asset, submit supported image model, complete provider/storage lifecycle
- Postconditions: output and ledger match UC-002; cross-user images are rejected
- Formal document references: `docs/VIDEO-OPERATIONS.md`

### UC-004: Signed provider callback
- Actor: configured AI provider
- Preconditions: stored provider/task binding and unexpired signed URL
- Flow: verify HMAC, parse payload, match provider/task, complete or fail
- Postconditions: one terminal transition and one corresponding ledger resolution
- Formal document references: `docs/spec/AI_PROVIDER_INTEGRATION.md`

### UC-005: Missed callback recovery
- Actor: QStash workflow/operator
- Preconditions: accepted nonterminal provider task
- Flow: poll provider durably through delays/failures until terminal or explicit escalation
- Postconditions: no indefinitely abandoned generation or credit hold
- Formal document references: `docs/VIDEO-OPERATIONS.md`, `docs/project-blueprint.md`

### UC-006: Subscription or credit purchase
- Actor: authenticated customer and Stripe
- Preconditions: valid price and Stripe configuration
- Flow: create checkout/portal session, return to app, verify webhook, reconcile entitlement
- Postconditions: existing return page and exactly-once economic update
- Formal document references: `docs/security-payment-operations.md`

### UC-007: Administrator operation
- Actor: authenticated administrator
- Preconditions: current database `isAdmin=true`
- Flow: access administrative page/API and perform an authorized operation
- Postconditions: operation succeeds for admin; guest/non-admin is denied
- Formal document references: admin route policy and `src/lib/auth/admin-role.ts`
