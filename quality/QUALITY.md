# Quality Constitution: VideoFly
> Generated by [Quality Playbook](https://github.com/andrewstellman/quality-playbook) v1.5.6 — Andrew Stellman
> Date: 2026-08-04 · Project: VideoFly

## Purpose

VideoFly is fit for use only when a user can authenticate, submit a supported generation, pay the advertised credits, receive a durable terminal result, and recover from vendor or webhook failures without unauthorized access or a stranded balance. A passing build is necessary but insufficient: the observable account state, stored media, provider task, payment record, and credit ledger must agree.

Deming's principle means these invariants are encoded in shared catalogs, server validation, state transitions, and repeatable tests. Juran's fitness-for-use standard means a paid generation ends as a usable video or an explicit failure with released credits. Crosby's principle means preventing duplicate charges, ownership violations, and unrecoverable jobs costs less than reconciling them after production incidents.

## Coverage Targets

| Subsystem | Target | Why |
|---|---:|---|
| Credit ledger and payment reconciliation | 95% branch coverage | Duplicate events or incomplete compensation directly alter customer value. |
| Video generation lifecycle and reconciliation | 90% branch coverage | Callback loss or long provider latency can strand videos and frozen credits. |
| Authentication, authorization, and ownership | 90% branch coverage | A single missed boundary can expose user media or administrative actions. |
| Provider routing, mapping, and callbacks | 90% branch coverage | Five provider representations can drift while TypeScript still compiles. |
| Upload and remote-media security | 90% branch coverage | External media combines ownership, content validation, SSRF, redirect, and size risks. |
| Billing navigation and public API contracts | 85% branch coverage | External payment redirects and frontend/backend payloads must resolve consistently. |
| Configuration and documentation contracts | 80% | Wrong secret names or missing deploy variables create production-only failures. |

## Coverage Theater Prevention

- An HTTP 200 assertion is insufficient without checking response status, ownership filtering, payload fields, and ledger effects.
- A mocked provider returning the configured mock value does not prove provider mapping, callback parsing, or fallback parity.
- Calling `freeze`, `settle`, or `release` without asserting package allocations and hold status is not a credit test.
- Checking that `/dashboard` appears in a Stripe request is not enough; the target must exist in the built route surface.
- Testing one provider identifier does not establish enumeration completeness across all configured providers.
- Testing an image MIME string without checking magic bytes and ownership does not establish safe upload behavior.
- A test that merely imports a module, asserts an object exists, or catches any exception is not coverage.

## Fitness-to-Purpose Scenarios

### Scenario 1: Guest submission crosses no paid boundary

**Requirement tag:** [Req: inferred — REQ-001]

**What happened:** A guest can fill the generator, but the request reaches no generation, upload, credit, or video mutation path. If a page-only login gate regresses while the API stays callable, anonymous requests could create vendor cost with no accountable user.

**The requirement:** Every sensitive API independently returns 401 without a valid session; the page redirect is defense in depth.

**How to verify:** Run the `REQ-001` functional checks and unauthenticated API matrix in `RUN_INTEGRATION_TESTS.md`.

### Scenario 2: Cross-user media is never accepted

**Requirement tag:** [Req: inferred — REQ-002]

**What happened:** A valid public-looking object URL can still belong to another account. If URL syntax is validated but reservation ownership is skipped, one customer can attach or operate on another customer's media.

**The requirement:** The authenticated database principal must own every referenced video and uploaded image.

**How to verify:** Create two users and assert list/get/delete/retry/generate reject the other user's identifiers without state changes.

### Scenario 3: Client model controls cannot lower server cost

**Requirement tag:** [Req: inferred — REQ-004]

**What happened:** A caller bypasses the UI and submits an unsupported duration, quality, audio flag, or output count. Without server-side catalog validation, vendor cost and charged credits can diverge while the UI still looks correct.

**The requirement:** The server validates capabilities and calculates cost from the shared active catalog.

**How to verify:** Run schema-valid mutations across active models and assert rejection or exact calculated credits.

### Scenario 4: Provider submission failure compensates atomically

**Requirement tag:** [Req: inferred — REQ-005]

**What happened:** Credits are frozen before an external provider call. A network or routing failure after the hold but before task binding must not leave a paid balance frozen or create a retryable orphan video.

**The requirement:** Submission failure releases the hold and marks the video FAILED exactly once.

**How to verify:** Inject failures before and after provider selection and assert hold, package, transaction, and video state.

### Scenario 5: A forged callback cannot complete another task

**Requirement tag:** [Req: inferred — REQ-006]

**What happened:** Callback URLs remain valid for up to 24 hours. A leaked or replayed URL must still fail when the provider identity or external task ID differs, otherwise media and charges can be bound to the wrong video.

**The requirement:** HMAC age/skew, provider, video UUID, and external task ID all match before transition.

**How to verify:** Tamper each binding independently and assert no video or credit mutation.

### Scenario 6: A slow task does not outlive reconciliation

**Requirement tag:** [Req: inferred — REQ-007]

**What happened:** The durable workflow currently polls ten times at 45-second intervals. A legitimate task still processing after roughly 7.5 minutes leaves the workflow PENDING; without requeue or terminal policy, a customer can see GENERATING and frozen credits indefinitely.

**The requirement:** Missed callbacks converge through durable retries or an explicit timeout that releases value safely.

**How to verify:** Keep a fake provider processing beyond the initial window and assert a later durable action reaches COMPLETED or FAILED with a resolved hold.

### Scenario 7: Duplicate Stripe delivery changes value once

**Requirement tag:** [Req: inferred — REQ-008]

**What happened:** Stripe retries webhooks and related invoice event types may describe the same economic payment. Without event/order idempotency, one payment can grant multiple credit packages or advance a plan twice.

**The requirement:** Signatures are verified and economic operations are claimed idempotently before ledger mutation.

**How to verify:** Replay identical and equivalent payment events concurrently; assert one order/package and one balance delta.

### Scenario 8: Legacy payment returns resolve to an actual account page

**Requirement tag:** [Req: inferred — REQ-009]

**What happened:** Checkout or Billing Portal may return to the legacy `/dashboard` path. The application middleware currently redirects that path to `/text-to-video`; a regression in this compatibility mapping could make a successful payment appear broken even though the payment itself completed.

**The requirement:** Every configured Stripe return target either resolves directly or has a tested middleware redirect, while preserving locale policy.

**How to verify:** Extract success, cancel, and portal URLs and assert each resolves directly or redirects to an existing localized route in a production build.

### Scenario 9: Provider media cannot reach private infrastructure

**Requirement tag:** [Req: inferred — REQ-010]

**What happened:** A provider-controlled media URL is checked by DNS and later fetched by hostname. DNS rebinding between those operations can redirect the actual connection to private infrastructure even though the preflight lookup was public.

**The requirement:** The connection destination must remain bound to a validated public address through redirects, and response bytes remain bounded.

**How to verify:** Use a controlled resolver/dispatcher test seam that changes DNS between validation and connection.

### Scenario 10: Adding a provider cannot create a partial integration

**Requirement tag:** [Req: inferred — REQ-011]

**What happened:** `bailian` exists in the type, configuration, API-key switch, and factory, while its supported completion path is polling through `getTaskStatus()` rather than callback ingress. Without explicit capability metadata, a future provider addition could compile while an actually required ingress or reconciliation path is missing.

**The requirement:** A canonical provider registry or mechanical parity check covers every representation and records explicit callback-versus-polling capability exceptions.

**How to verify:** Run `quality/mechanical/verify.sh` and provider-parametrized contract tests.

## AI Session Quality Discipline

1. Read this constitution and `REQUIREMENTS.md` before changing audited code.
2. Run targeted regression tests and the full suite before completion.
3. Preserve authorization, ledger, and state-machine invariants on every error path.
4. Add negative and concurrency coverage for external boundaries.
5. Never mark a vendor-chain test passed when it was skipped for missing credentials.
6. Update contracts and requirements when behavior intentionally changes.
7. Do not remove a scenario; supersede it with an explicit decision and evidence.

## The Human Gate

- Whether a long-running provider task should time out, continue indefinitely, or require manual review.
- Which account page is the canonical Stripe return destination and how locale is represented.
- Whether Bailian is intentionally polling-only or expected to accept callbacks.
- Production credential, Stripe, QStash, database, provider, and R2 verification.
- Authorization-policy changes, backward compatibility, refunds, and financial reconciliation decisions.
